Q2. Why store the token in localStorage?

Common answer:

So it persists after a page refresh.
The interceptor can read it and attach it to every request.

(For highly secure applications, cookies with HttpOnly are often preferred over localStorage to reduce XSS risk.)

-  HttpRequest objects are immutable (read-only). We cannot modify the original request, 
so we create a cloned request and add the Authorization header to the cloned request before forwarding it.

Ex:
import { inject } from '@angular/core';
import { Router } from '@angular/router';
import { HttpInterceptorFn,HttpErrorResponse } from '@angular/common/http';
import { catchError } from 'rxjs/operators';
import { throwError } from 'rxjs';

export const authInterceptor: HttpInterceptorFn = (req, next) => {
  // inject Router here
  const router = inject(Router);
  // get token here
  const token = localStorage.getItem('token');

  const authReq = token
    ? req.clone({
        setHeaders: {
          Authorization: `Bearer ${token}`
        }
      })
    : req;

  return next(authReq).pipe(

    catchError((error: HttpErrorResponse) => {

      if (error.status === 401) {

        // Remove expired token
        localStorage.removeItem('token');

        // Redirect to login page
        router.navigate(['/login']);
      }

      return throwError(() => error);

    })

  );

};

@Injectable({
  providedIn: 'root'

export class LoginGuard implements CanActivate {

  constructor(
    private authService: AuthService,
    private router: Router
  ) {}

  canActivate(): boolean {

    if (this.authService.isLoggedIn()) {

AuthGuard:

@Injectable({
  providedIn: 'root'
})
export class AuthGuard implements CanActivate {

  constructor(
    private authService: AuthService,
    private router: Router
  ) {}

  canActivate(route: ActivatedRouteSnapshot): boolean {
	// get token here
    const token = this.authService.getToken();

    if (!token) {
      this.router.navigate(['/login']);
      return false;
    }
	// hey roles here
    const userRoles = this.authService.getRoles();

    const allowedRoles =
      route.data['roles'] as string[];

    const hasAccess =
      allowedRoles.some(role =>
        userRoles.includes(role)
      );

    if (!hasAccess) {
      this.router.navigate(['/unauthorized']);
      return false;
    }

    return true;
  }
}

What is a Design Pattern?
A Design Pattern is a reusable solution to a commonly occurring software design problem. It is not code, but a proven way of structuring classes and objects.

Interview Definition:

A design pattern is a reusable, well-tested solution to a common software design problem. It provides a standard approach to designing software but is not a ready-made implementation.

Types of Design Patterns
1. Creational Patterns
----------------------
Purpose: How objects are created.

If an interviewer asks: "What problem does the Factory pattern solve?", give them this 3-point answer:

Suppose you don't use a factory.

The Factory Pattern removes this problem.

The Factory Pattern is a Creational Design Pattern that provides 
an interface for creating objects but allows a dedicated Factory class to decide which concrete class to instantiate at runtime.

// PaymentGatewayFactory.cs

public class PaymentGatewayFactory : IPaymentGatewayFactory
{
	private readonly IServiceProvider _serviceProvider;
	
	public PaymentGatewayFactory(IServiceProvider serviceProvider)
    {
        _serviceProvider = serviceProvider;
    }
	
	public IPaymentGateway getPaymentGetway(string gatewayType)
	{
		return gatewayType.ToLower() switch
		{
			case "Paypal" => _serviceProvider.GetRequiredService<Paypalgateway>(),
			      
			case "Stripe" => _serviceProvider.GetRequiredService<StripeGateway>(),
			default :
				throw new ArgumentException("Invalid payment gateway type");
		}
	
	}
}

Centralization: "It centralizes object creation logic. If we need to change how a PaymentGateway is created, we only change it in the Factory, not across the entire application."

Abstraction: "It allows the calling code to remain ignorant of concrete implementations. The Controller only works with IPaymentGateway, making the code loosely coupled."

Extensibility: "It makes the code Open for Extension but Closed for Modification. I can add GooglePay, ApplePay, or BitCoin by adding new classes and updating the Factory,

Q1. Why Factory Pattern?
Answer
Factory Pattern centralizes object creation. The client requests an object from the factory instead of creating concrete classes directly. 
This reduces coupling and makes the application easier to extend.


Q2. Why return an interface instead of a concrete class?
Answer
Because the controller should depend on an abstraction (IPaymentGateway) rather than a specific implementation (PaypalGateway). This follows the Dependency Inversion Principle.


Q3. Why use IServiceProvider?
Answer
Because it lets the DI container construct the object, automatically resolving any dependencies such as ILogger, HttpClient, or DbContext. 
The factory doesn't need to know how to build the object.


Q4. Which SOLID principles are used?
Open/Closed Principle – Add new gateways without changing the controller.
Dependency Inversion Principle – Depend on IPaymentGateway, not concrete classes.
Single Responsibility Principle – The controller handles requests, while the factory handles object creation.

																		2. Unit Of Work 
																		

In your microservices project (specifically the Ordering.API which uses SQL Server), you might have multiple repositories—for example, an OrderRepository and a CustomerRepository.

Without Unit of Work, if you update an Order and then update a Customer, you have to call _context.SaveChanges() twice. If the first one succeeds but the second one fails,

Quest > What is Unit Of Work
- The Unit of Work is a pattern that groups one or more operations (usually across multiple repositories) into a single transaction. 
It ensures that either all changes are committed to the database, or none of them are.

Quest > What recurring problem it solve
Concurrency: It prevents multiple repositories from opening multiple connections to the same database.

public class UnitOfWork : IUnitOfWork
{
    private readonly OrderContext _context;
    public IOrderRepository Orders { get; private set; }
    public ICustomerRepository Customers { get; private set; }

    public UnitOfWork(OrderContext context)
    {
        _context = context;
        Orders = new OrderRepository(_context);
        Customers = new CustomerRepository(_context);
    }

    public async Task<int> CompleteAsync()
    {
        return await _context.SaveChangesAsync();
    }

    public void Dispose() => _context.Dispose();
}

to increase api speed
async and await code = perform asynchronous calling using async and await (context switching)


class program
{
	static void Main(string[] args)
	{
		Method(); // call
		Console.WriteLine("Main Method");
		Console.ReadLine();
	}
	
	public static async void Method()
	{
		await Task.Run(new Action(LongTask)); // wait for response until main thread is running
		Console.WriteLine("New Thread");
	}
	public static void LongTask()
	{
		Thread.sleep(20000);
	}

}


What actually happens:

Main thread calls Method()
Main thread hits await → it pauses at that line and says "okay, you go run LongTask, tell me when done"
A background thread is created and runs LongTask() independently (sleeping 20 seconds)
Meanwhile, main thread is free — not frozen, not stuck
When background thread finishes, it sends the response back
Main thread wakes up and continues → prints "New Thread"


The background thread is like a restaurant kitchen — you (main thread) place the order and sit free to do other things. Kitchen (background thread) cooks. 
When food is ready, waiter calls you back. You didn't stand frozen at the counter the whole time.

Q>Why use Task.WhenAll?
Answer:
It executes multiple asynchronous operations concurrently, reducing the total execution time compared to awaiting each operation sequentially.

Q>Does Task.WhenAll create new threads?
Answer:
No.It doesn't create new threads. It waits for multiple asynchronous tasks that are already running to complete. The operations are typically I/O-bound,
 so they don't require dedicated threads while waiting.


Q>Why not write this?

await _httpClient.GetAsync("api1");

await _httpClient.GetAsync("api2");

Answer:
Because the second request starts only after the first one completes, increasing the total response time.


Q> When should you use parallel API calls?

Use them when:

APIs are independent.
One API doesn't depend on the result of another.

Examples:

Dashboard data
Product + Category lists
Customer + Orders
Multiple microservice calls

Don't use parallel execution when the second API depends on data returned by the first API.


 -- task.whenall() :
 
// GOOD: Parallel — all start together, wait once. Max time = longest task (1.5s)
public async Task<DashboardData> LoadDashboardParallel()
{
    // Fire all three immediately — they run concurrently
    var partnersTask = _partnerService.GetPartnersAsync();
    var transactionsTask = _txnService.GetSummaryAsync();
    var kycTask = _kycService.GetStatusAsync();

        Partners = partnersTask.Result,        // ✅ Safe — completed
        Transactions = transactionsTask.Result,
        KycStatus = kycTask.Result
    };
} 
Start all three, then WhenAll waits once. Time = longest task, not sum. On our Azure-hosted microservices, 
this was the difference between a snappy dashboard and a timeout."

Question 1> What is MemoryCache ?

MemoryCache is an in-memory caching mechanism in ASP.NET Core. It stores frequently used data in the server's RAM so you don't have to fetch it repeatedly from a database or external API.
Think of it like this:

Without Cache

User → API → Database → Response

With MemoryCache

User → API → MemoryCache → Response

If the data isn't in the cache:

User → API → Database → Save to Cache → Response

Step 4: Set Expiration

Absolute Expiration

Expires after a fixed time.

_memoryCache.Set(
    "products",
    products,
    TimeSpan.FromMinutes(10)
);

After 10 minutes, the cache is removed.


Sliding Expiration

Keeps the cache alive as long as it's being accessed.


_memoryCache.Set(
    "products",
    products,
    new MemoryCacheEntryOptions
    {
        SlidingExpiration = TimeSpan.FromMinutes(5)
    });
	
Example:

10:00 Request

10:04 Request

10:08 Request

10:12 Request

Cache never expires because it is continuously used.

If nobody requests it for 5 minutes, it expires.


Both Together

_memoryCache.Set(
    "products",
    products,
    new MemoryCacheEntryOptions
    {
        AbsoluteExpirationRelativeToNow = TimeSpan.FromHours(1),
        SlidingExpiration = TimeSpan.FromMinutes(10)
    });
	
This means:

If the cache is idle for 10 minutes, it expires.
Even if it is used constantly, it will be removed after 1 hour.

| Requirement                                 | Function         |
| ------------------------------------------- | ---------------- |
| Every row unique                            | `ROW_NUMBER()`   |
| Competition ranking                         | `RANK()`         |
| Highest, second highest, nth highest salary | `DENSE_RANK()` ✅ |


Q: Why use DENSE_RANK() instead of ROW_NUMBER()?
"ROW_NUMBER() assigns a unique number to every row, even when salaries are the same. For finding the second highest salary, 
DENSE_RANK() is more appropriate because employees with the same salary receive the same rank, and there are no gaps in the ranking."

Why do we use them?

They are serverless → you don’t manage servers.

They scale automatically → if 100 files are uploaded, Azure spins up more function instances.

They are event-driven → they only run when triggered.

Key Concepts (Beginner Level)
host.json → Settings for how functions behave (timeouts, retries, logging).

local.settings.json → Local development settings (connection strings, secrets).

Scaling → Functions scale based on events (queue length, blob uploads).

Timeouts → Consumption plan has 5 min limit, Premium plan allows longer.

Queue Trigger → Function runs when a message is added to a queue.

Blob Trigger → Function runs when a file is uploaded to Blob Storage.


In our project, we had a challenge where downloading loan documents from ICE Mortgage API took 10–30 minutes, which caused API timeouts. 
We solved this using Azure Functions and Queue-based async processing.
The client sends a request, we immediately return a TaskId, and enqueue the work. A queue-triggered Azure Function picks up the job, 
processes the documents step by step, and updates status in Azure Table Storage. 
The client can poll for status or get notified via webhook. This design avoids timeouts, scales automatically, and keeps the workflow reliable.

namespace HCL.Function
{
    public static class GstCalculator
    {
        [FunctionName("CalculateOrderGst")]   // we apply functionApp()
        public static async Task<IActionResult> Run(                              // Run on azure function on server
            [HttpTrigger(AuthorizationLevel.Function, "post", Route = null)] HttpRequest req,						// httptrigger
            ILogger log) 
        {
            log.LogInformation("Processing GST Calculation for a new order.");

            // 1. Read the Request Body
            string requestBody = await new StreamReader(req.Body).ReadToEndAsync();
            var data = JsonConvert.DeserializeObject<OrderRequest>(requestBody);

            if (data == null || data.BaseAmount <= 0)
            {
                return new BadRequestObjectResult("Please provide a valid BaseAmount.");
            }

            // 2. Logic: Apply GST (e.g., 18% standard)
            // In a real HCL project, you might fetch this rate from a Database
            decimal gstRate = 0.18m; 
            decimal gstAmount = data.BaseAmount * gstRate;
            decimal finalTotal = data.BaseAmount + gstAmount;

            // 3. Return a Structured Response
            return new OkObjectResult(new
            {
                BaseAmount = data.BaseAmount,
                GstRate = "18%",
                GstAmount = gstAmount,
                TotalPayable = finalTotal,
                Currency = "INR"
            });
        }
    }

    public class OrderRequest
    {
        public decimal BaseAmount { get; set; }
        public string Category { get; set; }
    }
}

public async Task DownloadInChunks(BlobClient blobClient, string localPath)
{
    var properties = await blobClient.GetPropertiesAsync();
    long fileSize = properties.Value.ContentLength;
    long chunkSize = 1 * 1024 * 1024; // 1MB chunks

    using var fileStream = File.OpenWrite(localPath);

    for (long i = 0; i < fileSize; i += chunkSize)
    {
        // Request a specific byte range
        var downloadInfo = await blobClient.DownloadAsync(new HttpRange(i, chunkSize));
        
        await downloadInfo.Value.Content.CopyToAsync(fileStream);
    }
}

bool CheckAnagram(string s, string t)
{
    // Step 1: Length check
    if (s.Length != t.Length)
    {
        return false;
    }

    // Step 2: ASCII frequency array
    int[] ch = new int[256];

    for (int i = 0; i < s.Length; i++)
    {
        ch[s[i]]++;   // Increase frequency of s string array
        ch[t[i]]--;   // Decrease frequency of t string array
    } 

    // Step 3: Check frequencies
    for (int i = 0; i < ch.Length; i++)
    {
        if (ch[i] != 0)
            return false;
    }

    return true;
}

public bool IsValid(string s) {
    // 1. Create our "Stack" of plates
    Stack<char> myStack = new Stack<char>();

    // 2. Look at every character in the string one by one
    foreach (char c in s) {
        // If it's an opening, push it to the stack
        if (c == '(' || c == '[' || c == '{') {
            myStack.Push(c);
        }
        // If it's a closing, we need to check the top
        else {
            // If we have a closing bracket but the stack is empty, it's wrong!
            if (myStack.Count == 0) return false;

            char top = myStack.Pop(); // Take the top plate off

            // Check if the pair is wrong
            if (c == ')' && top != '(') return false;
            if (c == ']' && top != '[') return false;
            if (c == '}' && top != '{') return false;
        }
    }

    // 3. If the stack is empty, return true. If stuff is left over, return false.
    return myStack.Count == 0;
}

Question : Immediate Execution vs Deferred Execution in Entity Framework Core ?


What is Deferred Execution?

Definition:

Deferred execution means the SQL query is NOT sent to the database immediately. The query is built in memory and executes only when the data is actually needed.

Hint : toList() is not applied 

Example:

var employees = context.Employees
                       .Where(e => e.Salary > 50000);

At this point:

❌ No SQL query has been executed.
EF Core has only created an IQueryable.

Execution happens here:

var result = employees.ToList();

Now EF Core generates SQL like:

SELECT *
FROM Employees
WHERE Salary > 50000;


Immediate Execution

Immediate execution means the query is executed immediately because you've requested the data.

Example:

var employees = context.Employees
                       .Where(e => e.Salary > 50000)
                       .ToList();
					   
As soon as ToList() is called:

✅ SQL is sent to SQL Server.
✅ Data is fetched.
✅ Results are stored in memory.

Pipes in Angular are used for data transformation in the template. there are two types of pipes pure and impure , By default, pipes are Pure, 
meaning they only execute when the input reference changes, which is highly optimized. 
Impure pipes -:

import { Pipe, PipeTransform } from '@angular/core';

@Pipe({
  name: 'filter',
  pure: false // This makes it an impure pipe.
})
export class FilterPipe implements PipeTransform {

  transform(items: any[], searchText: string): any[] {

    if (!searchText) {
      return items;
    }

    return items.filter(item =>
      item.name.toLowerCase().includes(searchText.toLowerCase())
    );
  }
}


| Pure Pipe                                           | Impure Pipe                                          |
| --------------------------------------------------- | ---------------------------------------------------- |
| `pure: true` (default)                              | `pure: false`                                        |
| Runs only when input reference changes              | Runs on every change detection cycle                 |
| Better performance                                  | Lower performance                                    |
| Suitable for formatting (currency, date, uppercase) | Suitable for filtering/searching mutable collections |


Q: Why are search/filter pipes usually impure?

Answer: Because the filtered result needs to update whenever the search text or collection changes. A pure pipe only runs when its input references change, 
whereas an impure pipe runs on every change detection cycle. However, for large applications,
 filtering in the component (using RxJS or signals) is generally preferred over an impure pipe for better performance.
 
 
 
 Should you use an impure search pipe?

In production, usually no.

Filtering in an impure pipe means the filter logic runs on every change detection cycle, which can become expensive for large lists.

A better Angular approach is to filter in the component using RxJS or signals.


Angular 17–22, use signals:


users = signal<User[]>([]);
searchText = signal('');

filteredUsers = computed(() =>
  this.users().filter(user =>
    user.name.toLowerCase().includes(this.searchText().toLowerCase())
  )
);


Then in the template:

@for (user of filteredUsers(); track user.id) {
  <div>{{ user.name }}</div>

RxJS: shareReplay() — Smart Caching
===================================

shareReplay(bufferSize)
  → Shares one subscription among multiple subscribers
  → Replays last N values to new/late subscribers
  → Prevents duplicate HTTP calls
  → Parameter: how many emissions to remember

shareReplay(1)  = remember last 1 value (most common)
shareReplay(3)  = remember last 3 values
shareReplay()   = remember ALL values (unbounded — use with caution!)

Use Case: API caching in Angular services
  → Employee 1 fetched? Don't fetch again!
  → Multiple components need same data? Share one call!

Important:
  → shareReplay() caches the Observable, not just the data
  → Cache persists for lifetime of the Observable
  → For cache expiration, use custom logic or switchMap with timer
  
  
  
  
RxJS: catchError + retry for Failed API Calls
=============================================

catchError(handler)
  → Catches error in stream
  → Can recover (return fallback) or rethrow
  → Must return new Observable

retry(count)
  → Retries immediately, count times
  → Simple but no delay between retries

retryWhen(errorObservable => logic)
  → Custom retry logic with delays
  → Use delay(), delayWhen(), timer() for spacing
  → Use take(n) to limit retries

Exponential Backoff Pattern:
  → delay = 2^retryCount * 1000ms
  → 1st retry: 2s, 2nd: 4s, 3rd: 8s...
  → Prevents overwhelming server

Best Practice:
  1. retryWhen with delay for transient errors
  2. catchError to transform error for UI
  3. shareReplay to avoid duplicate retries
  4. Component shows loading + error states




import { retryWhen, delay, take, catchError } from 'rxjs/operators';
import { timer } from 'rxjs';

getUserById(id: number) {
  return this.http.get(`https://jsonplaceholder.typicode.com/users/${id}`)
    .pipe(
      retryWhen(errors => 
        errors.pipe(
          delay(2000),     // ← Wait 2 seconds between retries
          take(3)          // ← Retry max 3 times
        )
      ),
      catchError(error => {
        return throwError(() => new Error('Service unavailable after retries'));
      })
    );
}

export class MyComponent {
  
  private http = inject(HttpClient);  // Modern Angular inject()

  // Define as class properties
  $users = this.http.get('https://jsonplaceholder.typicode.com/users');
  $posts = this.http.get('https://jsonplaceholder.typicode.com/posts');

  constructor() {
    // forkJoin waits for ALL to complete, then emits combined result
    forkJoin([this.$users, this.$posts]).subscribe({
      next: ([users, posts]) => {
        console.log('Users:', users);   // Array of users
        console.log('Posts:', posts);   // Array of posts
      },
      error: (err) => console.error('Error:', err)
    });
  }
}

| **Emits ONCE**       | Emits combined result as an array      |
| **Order preserved**  | Results in same order as input array   |
| **Fails fast**       | If ANY fails, entire forkJoin fails    |
| **Last values only** | Takes only last emission from each     |

// user.effects.ts
import { Injectable } from '@angular/core';
import { Actions, createEffect, ofType } from '@ngrx/effects';
import { switchMap, map, catchError, of } from 'rxjs';

@Injectable()
export class UserEffects {
  
  constructor(
    private actions$: Actions,
    private userService: UserService
  ) {}

  // ✅ Effect: Load User
  loadUser$ = createEffect(() => 
    this.actions$.pipe(
      ofType(UserActions.loadUser),           // Listen for "loadUser" action
      switchMap((action) =>                   // Cancel previous, switch to new
        this.userService.getUserById(action.id).pipe(
          map(user => UserActions.loadUserSuccess({ user })),   // Success action
          catchError(error => of(UserActions.loadUserFailure({ error }))) // Error action
        )
      )
    )
  );
}

| Problem                                              | `switchMap` Solution                       |
| ---------------------------------------------------- | ------------------------------------------ |
| User clicks "Load User 1" then quickly "Load User 2" | Cancels User 1 API call, only keeps User 2 |
| Multiple rapid actions fired                         | Only processes the **latest**              |
| Prevents race conditions                             | Old requests don't overwrite new results   |


Timeline with switchMap:
Action:     [Load User 1]─────[Load User 2]───────────

Result:                                User 2 data

Without switchMap (using mergeMap):
API Call 1:  ────────────────● (completes later!) ❌
API Call 2:           ────────● (completes first)

| ------------ | ------------------------ | --------------------------------- |
| `switchMap`  | Search, load latest data | Cancel previous, keep latest      |
| `mergeMap`   | Save/delete operations   | Process all, don't cancel         |
| `concatMap`  | Sequential operations    | Wait for each to finish           |
| `exhaustMap` | Login/submit buttons     | Ignore new until current finishes |




how to prevent memeory leaks in angular


Angular: Preventing Memory Leaks
=================================

Problem:
  → Subscriptions stay alive after component destroyed
  → Causes memory leaks, unexpected callbacks

Solutions:

1. Subscription Array (Manual)
   private subs: Subscription[] = [];
   this.subs.push(observable.subscribe(...));
   ngOnDestroy() { this.subs.forEach(s => s.unsubscribe()); }

2. takeUntilDestroyed() [Angular 16+]
   .pipe(takeUntilDestroyed())
   → Auto-unsubscribe when component destroyed
   → Only works in injection context

3. async Pipe (Recommended)
   data$ = http.get(...);
   template: {{ data$ | async }}
   → Angular handles subscribe/unsubscribe

4. takeUntil + Subject
   private destroy$ = new Subject<void>();
   .pipe(takeUntil(this.destroy$))
   ngOnDestroy() { this.destroy$.next(); this.destroy$.complete(); }

Best Practice:
  → Use async pipe for template data
  → Use takeUntilDestroyed() for component logic
  → Avoid manual subscription arrays when possible



| Method                     | Code                          | Auto-Cleanup | Best For                 |
| -------------------------- | ----------------------------- | ------------ | ------------------------ |
| **Subscription Array**     | `sub.push()` + `ngOnDestroy`  | ❌ Manual     | Simple components        |
| **`takeUntilDestroyed()`** | `.pipe(takeUntilDestroyed())` | ✅ Auto       | Modern Angular (v16+)    |
| **`async` pipe**           | `{{ data$ \| async }}`        | ✅ Auto       | Template-bound data      |
| **`takeUntil` + Subject**  | `.pipe(takeUntil(destroy$))`  | ⚠️ Manual    | Complex logic, re-usable |


Method 1:(subscription Array)

import { Component, OnDestroy } from '@angular/core';
import { Subscription } from 'rxjs';

@Component({...})
export class EmployeeComponent implements OnDestroy {
  
  private subscriptions: Subscription[] = [];

  getEmployees() {
    const sub1 = this.http.get('/api/employees').subscribe(res => {
      console.log(res);
    });
    this.subscriptions.push(sub1);
    
    const sub2 = this.someService.data$.subscribe(data => {
      console.log(data);
    });
    this.subscriptions.push(sub2);
  }

  ngOnDestroy() {
    this.subscriptions.forEach(sub => sub.unsubscribe());
  }
}


Method 2 : TakeUntilDestroy()


import { Component, inject } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';
import { SomeService } from './some.service';

@Component({
  selector: 'app-employee',
  template: `...`,
  standalone: true
})
export class EmployeeComponent {
  private http = inject(HttpClient);
  private someService = inject(SomeService);

  constructor() {
    this.getEmployees();
  }

  getEmployees() {
    // HTTP call - auto-completes on destroy
    this.http.get('/api/employees')
      .pipe(takeUntilDestroyed())
      .subscribe(res => {
        console.log(res);
      });

    // Long-lived observable - auto-completes on destroy
    this.someService.data$
      .pipe(takeUntilDestroyed())
      .subscribe(data => {
        console.log(data);
      });
  }
}



Method 3 : async pipe (template)


import { Component, inject } from '@angular/core';
import { Observable } from 'rxjs';

@Component({
  template: `
    <div *ngIf="employees$ | async as employees">
      <div *ngFor="let emp of employees">{{ emp.name }}</div>
    </div>
  `
})
export class EmployeeComponent {
  
  private http = inject(HttpClient);
  
  // ✅ Observable exposed to template
  employees$: Observable<any[]> = this.http.get<any[]>('/api/employees');
}

Question 1: What is Change Detection in Angular?
Change Detection is the mechanism Angular uses to detect changes in component data and automatically update the DOM.
 Whenever component properties change, Angular checks the bindings and refreshes the UI.
 
 
Question 2: What is the default Change Detection Strategy?
ChangeDetectionStrategy.Default

Angular checks the component whenever:

Button click
HTTP response
Promise
Observable
Timer
User input



Question 3: What is OnPush?
@Component({
  changeDetection: ChangeDetectionStrategy.OnPush
})
OnPush tells Angular to skip unnecessary change detection and only check the component when specific events occur, improving application performance.


Question 4: Why do we use OnPush?
Improves performance
Reduces unnecessary change detection
Best for large applications
Works well with immutable data

Question 10: Difference between Default and OnPush

| Default                    | OnPush                                      |
| -------------------------- | ------------------------------------------- |
| Checks frequently          | Checks only when triggered                  |
| Easier to use              | Better performance                          |
| Detects property mutations | Requires new references for `@Input` values |
| Suitable for small apps    | Suitable for large apps                     |


Question 17: Can we manually trigger change detection?
constructor(private cd: ChangeDetectorRef) {}
or 
this.cd.detectChanges();



Question 18: What is the difference between markForCheck() and detectChanges()?

markForCheck()

Marks the component to be checked in the next change detection cycle.

detectChanges()

Runs change detection immediately for the component and its children.

															** Angular Custom directives ***
															
A custom directive allows you to add custom behavior to existing HTML elements without modifying the element itself.
<input type="text" appNumberOnly>

Interview Question: Why did you create a custom directive?

In my project, I had multiple forms containing fields such as:

Pin Code
Phone Number
Employee ID
Customer ID

All these fields should accept only numeric values.

Instead of writing the same validation logic repeatedly in every component, I created a reusable custom directive.

Benefits:

Code reusability
Centralized logic
Easier maintenance
Cleaner HTML and TypeScript code
Consistent behavior across the application


Interview Question: Why not use Validators?
Answer

Validators validate data after it is entered.

Example:
Validators.pattern('^[0-9]*$')
User can still type:
abc123
and then Angular shows a validation error.

My directive prevents invalid input from being entered or paste in the first place.
So:
Directive = Prevention
Validator = Validation

In enterprise applications we often use both together.

import { Directive, HostListener } from '@angular/core';

@Directive({
  selector: '[appNumberOnly]'
})
export class NumberOnly {

  @HostListener('keydown', ['$event'])
  onKeyDown(event: KeyboardEvent) {
    const allowedKeys = ['Backspace', 'Tab', 'ArrowLeft', 'ArrowRight', 'Delete'];

    if ((event.key >= '0' && event.key <= '9') || allowedKeys.includes(event.key)) {
      return;
    }

    event.preventDefault();
  }

}

Interview Question: How did you implement it?
Answer

I used Angular's @Directive decorator and @HostListener.
@Directive({
  selector: '[appNumberOnly]'
})
This allows usage like:
<input appNumberOnly>
Then I listened to keyboard events:
@HostListener('keydown', ['$event'])
to block non-numeric keys.
And:
to block non-numeric keys.
@HostListener('paste', ['$event'])


Interview Question: Why HostListener?
Answer

HostListener allows a directive to listen to DOM events occurring on its host element.

Example:
@HostListener('click')
@HostListener('keydown')
@HostListener('paste')
Without manually attaching event listeners.

Interview Question: Where have you used custom directives?

You can answer:

I have used custom directives for:

Number-only input
Uppercase conversion
Auto focus
Disable double click
Role-based element visibility
Highlight invalid controls
Restrict special characters

Why Generic Repository?

Answer:
Generic Repository helps reduce duplicate CRUD code. Instead of creating separate repositories for Product, Category, Customer, etc., 
we write CRUD logic once and reuse it for all entities.


"Would you always use Generic Repository with EF Core?"

A strong answer is:

"Not always. EF Core already implements Repository and Unit of Work patterns through DbSet<T> and DbContext. For simple applications I often use EF Core directly. For large enterprise applications where I want abstraction, testability, or shared CRUD logic,

"Filters are components that execute before or after different stages of the MVC request pipeline. They help implement cross-cutting concerns such as 
authorization, logging, validation, exception handling, and response modification without duplicating code in controllers."

Why do we use Filters?

Suppose every API needs to:

| Exception Filter     | Handles exceptions thrown by actions                | When an exception occurs |
| Result Filter        | Runs before and after the action result is executed | Around the response      |

 Questions 1: Get the students who are taking Maths exam 
 
Solution 1 : (Nested Scalar Subquery) 
 
SELECT s.StudentName
FROM Student s
WHERE s.SubjectId IN
(
    SELECT sub.SubjectId
    FROM Subject sub
    WHERE sub.SubjectName='Maths'
);

Why use a subquery here?

Because:

First, find the SubjectId for Maths.
Then, find students whose SubjectId matches that value.


Is this a Scalar Subquery?

No.

This is a common interview trap.

A Scalar Subquery returns exactly one value.

Example:

SELECT *
FROM Student
WHERE SubjectId =
(
    SELECT SubjectId
    FROM Subject
    WHERE SubjectName = 'Maths'
);

Here, the inner query returns one value (1), so this is a Scalar Subquery.

Your query uses:

IN (...)

IN is designed to work with multiple values, so this is not called a scalar subquery. It is generally referred to as an IN subquery or a single-column subquery.


Solution 2 > use inner join

Most interviewers prefer this because it's more readable.

select s.studentName from 
Student as s
inner join
Subject as sub 
on s.subjectId = sub.subjectId
where sub.subjectName="Maths";



Interview Tip : Types of SubQuery

You should know these four common subquery types:

1> Scalar Subquery → Returns one value.

WHERE Salary > (SELECT AVG(Salary) FROM Employee)

2> Multi-row Subquery → Returns multiple rows.

WHERE DepartmentId IN (SELECT DepartmentId FROM Department)

3> Correlated Subquery → Inner query depends on the outer query.

SELECT *
FROM Employee e1
WHERE Salary >
(
    SELECT AVG(Salary)
    FROM Employee e2
    WHERE e1.DepartmentId = e2.DepartmentId
);


4> Nested Subquery → A subquery inside another subquery.

Q1. What is an Exclusive Lock?

Answer

It is a lock SQL Server places during INSERT, UPDATE, or DELETE operations. 
While an Exclusive Lock exists, other transactions cannot modify the same data, and under the default isolation level they cannot read the uncommitted changes.


Q2. What does WITH (NOLOCK) do?

Answer

It allows SQL Server to read data without acquiring a shared lock and without waiting for exclusive locks. 
This improves concurrency but can result in dirty reads because uncommitted data may be returned.



Q3. Is NOLOCK good?

Best answer:

It improves performance and reduces blocking for read-heavy queries, but it sacrifices consistency by allowing dirty reads. 
It should only be used when occasional inaccurate data is acceptable.

Easy Memory Trick

| Lock          | Used By                      | Other Reads Allowed?  | Other Writes Allowed? |
| ------------- | ---------------------------- | --------------------- | --------------------- |
| Shared (S)    | `SELECT`                     | ✅ Yes (other readers) | ❌ Writers wait        |
| Exclusive (X) | `INSERT`, `UPDATE`, `DELETE` | ❌ Normally wait       | ❌ Wait                |


What is a deadlock?

A deadlock occurs when two or more transactions each hold locks that the others need, causing all of them to wait indefinitely. SQL Server detects the deadlock automatically, 
selects one transaction as the deadlock victim, rolls it back, and allows the other transaction to continue.




What is UPDLOCK?

Answer:

UPDLOCK places an Update Lock instead of a Shared Lock during a read operation. It indicates that the transaction intends to update the row later,
 reducing the likelihood of lock-conversion deadlocks.
 
 
 Does UPDLOCK eliminate all deadlocks?

No.

This is a favorite interview question.

Correct answer:

No. UPDLOCK helps reduce certain deadlocks, particularly those caused by lock conversion from Shared to Exclusive locks. However, 
deadlocks can still occur due to inconsistent resource access order or other locking patterns.

Example : create class Sales contain InvoiceNumber as int but for future we want alphnumerice character for new customer

Question > How do you optimize a stored procedure?
	
1: Analyze the execution plan.
2: Check for missing or inefficient indexes.
3: Avoid SELECT *.
4: Rewrite queries to be SARGable (avoid functions on indexed columns in WHERE).
5: Reduce unnecessary scans, sorts, and joins.
6: Replace cursors with set-based operations where possible.
7: Use EXISTS instead of COUNT for existence checks.
8: Return only the required rows and columns.
9: Investigate parameter sniffing if performance varies by parameter.
10: Keep transactions short and maintain indexes/statistics.


Lets discuss .

1. Check the Execution Plan (Most Important)

This should always be your first step.

SELECT *
FROM tblEmployee
WHERE DepartmentId = 5;

Press:

Ctrl + M

or enable Include Actual Execution Plan.

Look for:

Table Scan ❌
Index Scan ⚠️
Index Seek ✅
Missing Index ⚠️
Expensive operators (Sort, Hash Match, Nested Loop)



2. Create Proper Indexes

Suppose:

SELECT *
FROM tblEmployee
WHERE DepartmentId = 5;

// here DepartmentId is primary key of Table tblEmployee


3. Never use SELECT *

Bad

SELECT *
FROM tblEmployee;


Good

SELECT EmployeeId,
       EmployeeName,
       Salary
FROM tblEmployee;


Reading fewer columns means:

Less disk I/O
Less network traffic
Less memory


4. Avoid Functions in WHERE Clause

Bad

WHERE YEAR(DateOfBirth)=2025

SQL Server must compute YEAR() for every row, so indexes on DateOfBirth can't be used efficiently.

Good

WHERE DateOfBirth >= '2025-01-01'
AND DateOfBirth < '2026-01-01'

This allows an index seek.


5. Avoid Leading Wildcards

Bad

WHERE Name LIKE '%John%'

Usually results in a table/index scan.

Better

WHERE Name LIKE 'John%'

This can use an index.


6. Avoid Cursors When Possible

Bad

CURSOR

Processes rows one at a time (RBAR: Row By Agonizing Row).

Better

UPDATE tblEmployee
SET Salary = Salary + 1000
WHERE DepartmentId = 5;

Set-based operations are almost always faster.


7. Return Only Required Rows

Bad

SELECT *
FROM tblEmployee;

Good

SELECT TOP 100 *
FROM tblEmployee;


or use paging:

OFFSET 0 ROWS
FETCH NEXT 20 ROWS ONLY;


8. Avoid Unnecessary Temp Tables

Sometimes developers do:

SELECT *
INTO #Temp
FROM tblEmployee;

If the temporary table isn't needed, query the original table directly.

Use temp tables only when they simplify or improve performance.



9. Use EXISTS Instead of COUNT (When Checking Existence)

Bad

IF (
    SELECT COUNT(*)
    FROM tblEmployee
    WHERE EmployeeId = 10
) > 0

Good

IF EXISTS
(
    SELECT 1
    FROM tblEmployee
    WHERE EmployeeId = 10
)


10. Avoid Unnecessary DISTINCT

Bad

SELECT DISTINCT EmployeeName
FROM tblEmployee;

DISTINCT often forces a sort or hash operation.

Only use it when duplicates truly need to be removed.



11. Use Proper JOINs

Instead of:

SELECT *
FROM Employee, Department
WHERE Employee.DepartmentId = Department.DepartmentId;


Use:

SELECT *
FROM Employee E
INNER JOIN Department D
ON E.DepartmentId = D.DepartmentId;

This is clearer and avoids accidental Cartesian products.



12. Avoid Repeated Queries

Bad

SELECT Name
FROM Employee
WHERE EmployeeId = 1;

SELECT Salary
FROM Employee
WHERE EmployeeId = 1;


Good

SELECT Name,
       Salary
FROM Employee
WHERE EmployeeId = 1;

One trip instead of two.




question > Function vs Stored Procedure


| Feature                                 | Function                                                   | Stored Procedure                     |
| --------------------------------------- | ---------------------------------------------------------- | ------------------------------------ |
| Purpose                                 | Returns a value                                            | Performs an action or business logic |
| Return Type                             | **Must** return a value                                    | May or may not return a value        |
| Can return table?                       | ✅ Yes (Table-Valued Function)                              | ❌ No (returns result sets instead)   |
| Parameters                              | Input parameters only                                      | Input and Output parameters          |
| Can modify data (INSERT/UPDATE/DELETE)? | ❌ No (SQL Server functions cannot modify permanent tables) | ✅ Yes                                |
| Can call transaction?                   | ❌ No                                                       | ✅ Yes                                |
| TRY...CATCH                             | ❌ No                                                       | ✅ Yes                                |
| Can call another procedure?             | ❌ No                                                       | ✅ Yes                                |
| Can be used inside SELECT?              | ✅ Yes                                                      | ❌ No                                 |
| Can be used in WHERE clause?            | ✅ Yes                                                      | ❌ No                                 |
| Execution                               | Called as part of a query                                  | Executed using `EXEC` or `EXECUTE`   |
| Best for                                | Calculations, reusable logic                               | CRUD operations, business workflows  |



Function Example

Suppose you want to calculate bonus.

CREATE FUNCTION fn_CalculateBonus
(
    @Salary DECIMAL(10,2)
)
RETURNS DECIMAL(10,2)
AS
BEGIN
    RETURN @Salary * 0.10;
END


Use it like this:

SELECT
    EmployeeName,
    Salary,
    dbo.fn_CalculateBonus(Salary) AS Bonus
FROM tblEmployee;


Output

Employee     Salary     Bonus
--------------------------------
John         50000      5000
Amit         60000      6000

Notice how the function behaves like a built-in SQL function such as UPPER() or LEN().
