--Exclusive Lock (X) - The "Writers" Lock
--When you run an UPDATE, INSERT, or DELETE, SQL Server automatically applies an Exclusive Lock to that row.

--The Rule: Only one person can have an Exclusive lock on a piece of data at a time.

--Behavior: If I am updating Row #4, you cannot update it, and you cannot even read it (unless you use a special hint like NOLOCK).
-- for nolock used only when doesnt matter what don't care if the data is 100% final, just show me what's there right now,

-- SELECT Price FROM tblProducts WITH (NOLOCK) WHERE id=4; -- here tbl

 -- dirty reed : when user1 perform update only that time user2 read data then user2 get different value so avoid the while update exculsive lock apply
 -- and no one read it (no share lock access) or update it 

--Purpose: To prevent two people from changing the same value at the exact same millisecond, which would cause data corruption.

--2. Shared Lock (S) - The "Readers" Lock
--When you run a SELECT query, SQL Server applies a Shared Lock.

--The Rule: Many people can hold Shared locks on the same data at the same time.

--Behavior: If I am reading Row #4, you can also read Row #4. We are "sharing" the view.

--Duration: By default (in "Read Committed" mode), a Shared lock is very short-lived. It is released as soon as the data is read.

--The Conflict: If I am reading a row (Shared lock), and you try to update it (Exclusive lock), you have to wait until I am done reading.

 --Pessimistic Locking (The "Safe" Approach)This uses the Database Locks ($S$, $X$, $U$) we just discussed.
 --You "hold" the lock for the entire duration of your business logic.How it works: 
 --1.  User A reads a row with an UPDLOCK.
    -- But if you know you are going to update that row in a second, you use UPDLOCK
	-- It tells the database: "I'm just reading for now, but I'm about to update this, so don't let anyone else even start a shared lock here."
	-- This prevents deadlocks before they even start.

 --2.  The database blocks User B from even starting an update.
 --3.  User A finishes their work and commits
 --4.  Only then can User B access the row.Best for: High-conflict data (like a bank withdrawal or a "last 5 items in stock" flash sale).Downside: 
 --It makes the application slow because people are constantly waiting in line (Blocking).



-- 2. Optimistic Locking (The "Modern" Approach)
--This does not use database locks while the user is thinking or typing. Instead, it uses a Version Number or a Timestamp.

--How it works:

--User A reads Row #4. The system notes that the Version is 1.

--User A takes 5 minutes to type a new name. (No locks are held in the DB).

--When User A clicks "Save," the app runs a query like this:
--UPDATE tblCustomer SET Name='New', Version=2 WHERE id=4 AND Version=1

--The Result: * If the row was updated by someone else, the Version would be 2, the WHERE clause would fail, and the app would say:
-- "Someone else updated this while you were away!"

--If no one touched it, the update succeeds.

--Best for: Most web applications and Angular frontends where users might leave a screen open for a long time.

--Downside: If two people do edit at the same time, the second person loses their work and has to start over.



--Pessimistic Locking																	Optimistic Locking
--Locked from Read until Commit.(Lock Timing)										no locked until save

--SQL Locks ($S, X, U$).																Versioning / RowVersion / Timestamps.
--share lock - read
--exclusive lock - write
--updlock - no one should write it until complete my work

 --1. Atomicity (The "Switch")
--The Focus: The Action.

--The Idea: It’s like a light switch; it’s either ON or OFF.

--Simple View: If you are moving money from Bank Account A to Bank Account B, you can't just subtract from A and "forget" to add to B. It’s both or neither.

--2. Consistency (The "Rules")
--The Focus: The Database Integrity.

--The Idea: The database must follow the rules (Constraints).

--Simple View: If your table has a rule that "Balance cannot be negative," and a transaction tries to take more money than you have, Consistency steps in and says "Stop! This breaks the rules, rollback now."

--3. Isolation (The "Privacy")
--The Focus: The Traffic Jam.

--The Idea: Even if 1,000 people are buying the same concert ticket at the same time, the database treats each person as if they are the only one there.

--Simple View: Transaction A shouldn't be able to "see" what Transaction B is doing until Transaction B is totally finished.

--4. Durability (The "Hard Drive")
--The Focus: The Safety.

--The Idea: Once the "Success" message pops up, that data is safe even if the building loses power one second later.

--Simple View: The data isn't just sitting in the "RAM" (temporary memory); it has been written to the physical disk (the log files).

--Conssitency = if bank amount is negative then no amount debited bcoz rule or constraint need to following
--Isolation = when transaction from bank A to bankB perform no one should stop ir not gonna impact from outside
--Durability = transaction donw then save it

 ----------------------------------------------------------------------------------------------------
 -- 1> Atomicity : required that tracsaction that involves two or more discrete parts of information  must commit 
 --                  all parts or more
  -- Ex: begin tran , commit tran

 -- 2> Consistency : required that transaction must create a valid state of new data, or it must rollback
 --                    all data to the state that existed before the transaction was executed
 -- ex : begin tran , save tran

 -- 3> Isolation : required that a transaction that is still running and did not commit all data yet , must stay 
 --					isolated from all other transactions
 -- isolation level

 -- 4> Durability : required that committed data must be stored using method that will preserve all data 
 --					in correct state and avilable to user , even in the case of a failure  
--  backup , commit 

--Atomicity → All or nothing.

--Consistency → Data integrity preserved.

--Isolation → Transactions don’t step on each other.

--Durability → Once saved, always saved.

create or alter procedure GetLastName
	@Name nvarchar(max)
As 
Begin
	set nocount on
	declare @firstName nvarchar(max);
	declare @lastName nvarchar(max);
	 -- Create a temp table first
    -- Split the name into a temp table
    SELECT value INTO #temp1 
    FROM string_split(@Name,' ');
	 -- Get the last name (everything except first word)
    --SELECT @lastName = STRING_AGG(value, ' ')
	SELECT *
    FROM #temp1
    WHERE value NOT IN (SELECT TOP 1 value FROM #temp1 ORDER BY (SELECT NULL));

    -- Return results
    SELECT @firstName AS FirstName, @lastName AS LastName;
	
End

EXEC GetLastName @Name = 'Farukh shaikh';

-- CTE is a temporary result set which can be used in the subsequest  execution scope only once

-- Example 

WITH Sales_CTE as
(                                    -- temporary result set
	select  [EmpName],
	[Gender] , [Email]
	from 
	tblEmployee
)
select * from Sales_CTE;

-- note : after creation of CTE , in the same subsequent context you can execute multiple times 
--        if the context  changes you (another query seperate) can not use it any more 

-- CTE mostly use for recursive

with recursiveCTE as
(
	select 1 as n 
	union all
	select n+1 from recursiveCTE where n<3
)
select * from recursiveCTE;

 -- Quest - How to optimize query
 -- Check Indexes: Ensure WHERE and JOIN columns are indexed.

--SARGability: Don't use functions on columns in the WHERE clause.

--No SELECT *: Only pull required columns.

--Execution Plan: Use tools to find "Scans" vs "Seeks."

--Batching: For huge updates, do them in small chunks (e.g., 5000 rows at a time) to avoid locking the whole table

------------------------------------------------------------------------------------------------------------

--quest > optimize stored procedure

--SET NOCOUNT ON: Reduces network traffic by stopping SQL from sending "rows affected" messages after every statement.

--Use Try-Catch: Provides structured error handling and ensures transactions are safely rolled back if a failure occurs.

--Select Specific Columns: Improves performance and memory usage by avoiding SELECT * and allowing for covering indexes.

--Use EXISTS instead of IN: Speeds up queries by using "short-circuit" logic that stops searching as soon as the first match is found.

--Schema Prefixing: Always use dbo.TableName to help SQL Server jump directly to the object without searching the schema list.

--Avoid Cursors: Use set-based logic (JOINs/Updates) instead of row-by-row loops to take advantage of SQL's parallel processing.

--Parameter Sniffing: Use local variables or RECOMPILE hints to prevent SQL from using an inefficient execution plan for specific parameters.

--Temporary Tables vs Variables: Use #TempTables for large datasets to allow indexing, and @TableVariables for small datasets to save memory.

--SARGable Queries: Avoid using functions (like YEAR() or LEFT()) on columns in the WHERE clause so SQL can use the B-Tree index.

--Update Statistics: Regularly update database statistics so the Query Optimizer has accurate information to choose the fastest path.
